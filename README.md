# Magnat

Nuxt + Supabase на сервере, Tauri-оболочки для Windows, macOS Apple Silicon, Android и iOS.

## Обновление сайта и приложений

Новые оболочки 0.2.3 открывают `https://192.168.10.250/?native=1&appVersion=0.2.3`. Интерфейс хранится на сервере,
а не в установщике. Пересборка и перезапуск контейнера Nuxt доставляют изменения на сайт
и в приложения. Изменения схемы Supabase требуют применения миграций.
Адрес сервера должен оставаться постоянным и доступным устройствам (для локального IP
настройте постоянную аренду DHCP в вашей сети).

При повторном открытии оболочка загружает актуальную страницу. Уже открытая оболочка
проверяет `/api/app-version` раз в 30 секунд и при возврате в приложение. После изменения
сборки страница перезагружается в состоянии покоя. Фокус в поле ввода, открытый диалог и
несохранённые изменения в полях откладывают перезагрузку до закрытия формы/смены раздела.
Ошибки запроса во время перезапуска сервера не показываются пользователю; проверка повторяется.

Автоматической установки обновлений оболочки нет. В меню приложения под «Копия личного хранилища» доступна страница «Версия приложения»: установленная версия, актуальный релиз и переход к загрузке. При запуске устаревшей версии появляется окно «Перейти и скачать / Позже / Закрыть». Новые установщики нужны при изменении
Tauri, Rust/нативных плагинов, разрешений ОС, иконок, версии оболочки или адреса сайта.
Для перехода со старой версии со встроенным интерфейсом нужно один раз установить новую оболочку.
При первом запуске после смены адреса загрузки может потребоваться повторный вход в аккаунт.

Оболочка разрешает сайту только явно перечисленные нативные действия: открытие ссылок, сохранение файлов, уведомления и чтение установленной версии. Веб-приложение работает с теми же
серверными API и проверками доступа, что и браузер. Для сборок с HTTP в локальной сети на Apple-платформах
есть ATS-настройки локальных соединений, на Android — исключение только для хоста сервера.
Android 17+ запрашивает разрешение доступа к локальной сети.

## Вход по QR-коду

На настольном экране входа справа от формы расположен QR-код. Обычная камера телефона
открывает `/auth/qr`; страница предлагает открыть Magnat через `magnat://auth/qr`,
а при отсутствии приложения остаётся доступен вход и подтверждение в браузере.
Обработка ссылок требует оболочки 0.2.3 или новее. В локальной сети вместо Universal Links
используется собственная схема: браузер может запросить разрешение на открытие приложения
или потребовать нажатия «Открыть в приложении Magnat».

Телефон должен быть авторизован. Пользователь сверяет шестизначный код и подтверждает
конкретное устройство; компьютер получает новую независимую сессию. QR действует две минуты,
обновляется кнопкой и используется один раз. Переход по ссылке сам по себе не подтверждает вход.
Секрет получения сессии остаётся на компьютере; в QR передаётся отдельный секрет подтверждения
во фрагменте ссылки. В таблице `qr_login_requests` (миграция 039) хранятся только хеши секретов,
чтение и запись доступны только серверу. Истёкшие запросы удаляются при создании следующего QR.
`MAGNAT_SERVER_URL` задаёт адрес QR-ссылок, доступный телефону, в том числе при открытии сайта
на компьютере через localhost. Телефон должен иметь доступ к этой сети и доверять сертификату сервера.

Проверка типов: `npm run typecheck`. При проверке QR-сценария проверьте подтверждение и
отклонение входа, истечение срока, повторное использование и независимость сессии компьютера.

## Сборка оболочек

`MAGNAT_SERVER_URL` — постоянный HTTP(S) origin. Текущий выбранный адрес — HTTPS на внутреннем IP. Клиентам Windows, macOS и iOS нужно доверять офисному CA из `deploy/windows-server/magnat-root.crt`; для Android он включается в сборку переменной `MAGNAT_ANDROID_CA_CERT` только для хоста сервера.
`MAGNAT_IOS_TEAM` — идентификатор существующей команды Apple для подписи iPhone-приложения.
Версия оболочки хранится в `src-tauri/tauri.conf.json` и `src-tauri/Cargo.toml`.

```sh
npm run macos:build
npm run windows:build          # внутри Windows
npm run android:release       # release APK с постоянным keystore
npm run ios:build -- --export-method debugging
```

Сборки не запускают Nuxt generate: `frontendDist` — URL сервера. `scripts/shell-config.mjs`
проверяет origin, создаёт конфигурацию удалённой страницы и отключает updater-артефакты.
`scripts/prepare-shell.mjs` создаёт платформенную конфигурацию для CI и iOS.
`npm run android:build` оставлен для debug APK; публичные загрузки используют release-вариант.

Мобильные иконки — существующий красный логотип Magnat из `public/favicon.svg`.
Обновляйте `src-tauri/icons`, `gen/android/app/src/main/res/mipmap*` и
`gen/apple/Assets.xcassets/AppIcon.appiconset` вместе при изменении логотипа.

## Отдельный workflow установщиков

`.github/workflows/release.yml` запускается вручную или при изменении нативных файлов
`src-tauri/**` и скриптов сборки оболочки в main. Изменения обычных страниц Nuxt, CSS,
серверных API и Supabase не запускают сборку установщиков.
Последовательность: Windows → macOS → Android → iOS → публикация.
В админке **Версии приложения** укажите следующую версию оболочки и описание для страницы загрузок.
После публикации версия неизменяема; следующий выпуск должен иметь больший номер.

Нужны self-hosted runners с меткой `magnat-ssd`: Windows и macOS. Node 24.15+, Rust 1.90+,
Windows C++ Build Tools/MSVC, Xcode/iOS SDK, Android SDK/NDK/JDK должны быть подготовлены.
Оба runner должны видеть одну папку релизов на SSD (Windows VM — через общую папку диска).
Рабочий каталог runner, `CARGO_HOME`, `CARGO_TARGET_DIR`, `RUSTUP_HOME`, `GRADLE_USER_HOME`,
`NPM_CONFIG_CACHE` и `TMPDIR` размещаются на SSD и проверяются `scripts/release-storage.mjs`.
На Windows `TEMP` и `TMP` тоже должны указывать на SSD.
Для Android дополнительно задаются `ANDROID_HOME`, `NDK_HOME`, `JAVA_HOME`.

Variables GitHub: `MAGNAT_SERVER_URL`. Secrets: `RELEASES_BUILD_TOKEN` (тот же, что
`NUXT_RELEASES_BUILD_TOKEN` на сайте), `ANDROID_KEY_BASE64`, `ANDROID_KEY_ALIAS`,
`ANDROID_KEY_PASSWORD`, при отдельном пароле хранилища `ANDROID_STORE_PASSWORD`.
Закрытые ключи и keystore не хранятся в Git. Постоянный keystore нельзя терять или менять
между версиями Android. Подпись updater больше не требуется.

CI сохраняет iOS-архив без подписи для разработчика. Установка на iPhone выполняется отдельно
с Apple Development-подписью и зарегистрированным устройством. IPA для такого устройства не
является универсальной установкой из App Store. Профиль имеет срок действия Apple.

## Страница скачивания и SSD

`/downloads` доступна без входа. Backend читает завершённый релиз из `NUXT_RELEASES_DIRECTORY`.
В Docker `.env` задаёт `MAGNAT_RELEASES_DIR` как путь на хосте, а
`NUXT_RELEASES_DIRECTORY=/releases`; папка монтируется в контейнер только для чтения.
Для админского плана релиза применяется миграция `026_app_releases.sql`.

```text
releases/
  latest.json
  0.2.0/
    release.json
    Magnat-0.2.0-windows-x86_64.exe
    Magnat-0.2.0-macos-aarch64.dmg
    Magnat-0.2.0-android-arm64.apk
    Magnat-0.2.0-ios-device.ipa   # только если подписан для зарегистрированного устройства
  .staging/
```

Новая версия становится доступна после проверки всех пакетов и атомарной смены `latest.json`.
Предыдущие версии сохраняются на SSD. Если диск отключён, backend не создаёт папку на внутреннем
диске вместо него. Для повторного запуска CI используйте Re-run all jobs.

## Windows Server

Схема размещения на CRM (E:), HTTPS, расположение данных и команды запуска описаны в [deploy/windows-server/README.md](deploy/windows-server/README.md). При нулевом числе непрочитанных уведомлений нативный счётчик на иконке полностью убирается.

### Локальный помощник Qwen3

`docker compose up -d --build` запускает Ollama. Для первой загрузки модели
выполните `docker compose --profile model-setup run --rm ollama-init`: команда
загружает `qwen3:0.6b` в постоянный том `ollama-models` и удаляет загрузчик. Интернет нужен
для первой загрузки образа и модели; запросы обрабатываются локально, облачные
возможности отключены (`OLLAMA_NO_CLOUD=true`). Порт Ollama не опубликован.
Лимиты сервера модели: **2 CPU, 2 ГиБ RAM, без дополнительного swap**;
одна модель и один запрос одновременно, контекст 4096 токенов. Через 10 минут
простоя модель выгружается из RAM. Загрузчик ограничен 1 CPU и 512 МиБ RAM.

После входа и разблокировки хранилища кнопка **«Помощник»** появляется внизу
справа. Например: «Добавь доступ к GitLab, логин alex, сайт https://gitlab.com».
Для явного создания из описания есть кнопка **«Подготовить карточку»**.
Нажмите **«Проверить и добавить в связку»**: откроется существующий редактор
карточки, где можно проверить данные и выбрать нужные связки. Сохранение
выполняется обычной кнопкой редактора с действующими проверками прав.
Если пароль не указан, он генерируется криптографическим генератором в браузере.
Модель получает последние сообщения чата и при необходимости сводку доступных данных:
выбранного проекта, задач Кабана и явных связей карточек с подписками. Значения
паролей, логины и секретные заметки хранилищ в сводку связей не входят.
Чат хранится в памяти страницы; очистка, блокировка и выход удаляют его.

Проверка модели: `docker compose exec ollama ollama list`.
Повторная установка модели: `docker compose --profile model-setup run --rm ollama-init`.
Для запуска Nuxt вне Docker задайте `NUXT_OLLAMA_URL` для локального Ollama;
публикация порта модели в стандартном Compose намеренно отключена.

Помощник также отвечает на вопросы о сервисах по публичной справке из
`shared/utils/assistant-help.ts`. Он получает только известный раздел страницы,
без ID записей, параметров URL и содержимого документов. Ссылки под ответом
ведут в разделы сайта. При изменении функций обновляйте справочник. Черновик
остаётся в чате: сообщение «сайт https://example.com» дополняет его, а вопрос
«как добавить пароль?» открывает разговор со справкой, без создания карточки.


Чат использует компоненты `UChatMessages`, `UChatPrompt`, `UChatPromptSubmit` и
`UChatShimmer` по структуре [Nuxt UI Chat template](https://github.com/nuxt-ui-templates/chat).
Ответ идёт потоком SSE от локальной Ollama, есть остановка и индикация набора.
Содержимое чата не сохраняется на сервере.

Боковой панели контекста нет. Если данных для запроса недостаточно, помощник
предлагает проекты, хранилища, сотрудников или карточки прямо в диалоге.
Выбор продолжает исходный запрос; выбранный проект и сотрудник сохраняются
до нового диалога. Для проектов доступны показатели, договоры, входные данные и
состояние этапов. Неполные или недоступные источники отмечаются в контексте.
Модель не получает произвольных инструментов или URL для вызова API.

Команда создания/изменения/переноса задачи без вызова модели предлагает
хранилище, затем открывает панель параметров. Хранилища только для просмотра
нельзя выбрать для изменения задач. Общие вопросы о странице «Финансы»
отвечают по справке сайта; вопросы о финансах проекта читают его показатели.
Должности берутся из профилей сотрудников с учётом компании и видимости.
Исполнение использует существующие API Кабана с проверками прав, автора,
категорий, завершения и ревизии. При переносе сервер сохраняет остальные поля.
Скрепка и перетаскивание файлов открывают выбор места загрузки: договор,
карточка входных данных или конкретное поле вложений задачи. До 20 файлов
за выбор, каждый до 20 МБ; действуют также ограничения места назначения.
Загрузка не означает разбор содержимого файла моделью.

Проверки:
`node --experimental-strip-types --test tests/assistant.test.mjs`;
`docker compose exec -T app node --input-type=module < tests/assistant-work.integration.mjs`.
Интеграционный тест создаёт и удаляет только собственные изолированные фикстуры.

Запросы к модели выполняются по очереди: один активный, до 12 ожидающих и
не более двух запросов от одного аккаунта одновременно. В чате видно место
в очереди; остановка удаляет ожидающий запрос или прерывает генерацию.
Ожидание ограничено 10 минутами, таймаут самой генерации начинается после
получения слота. Очередь находится в памяти единственного контейнера Nuxt и
сбрасывается при его перезапуске. Для нескольких реплик потребуется общая очередь.
Позиции передаются через SSE, без имён, вопросов или идентификаторов других людей.

Повторяющийся ответ останавливается с отменой запроса Ollama. Незавершённый
фрагмент удаляется из чата и не используется в следующем вопросе. Вопросы
«какой у меня пароль от …» обрабатываются по доступным метаданным карточек:
помощник предлагает открыть подходящую карточку, не передавая секрет модели.
Проверки очереди с реальными подключениями:
`docker compose exec -T app node --input-type=module < tests/assistant-queue.integration.mjs`.


Фактические вопросы о проектах обслуживает `server/utils/assistant-read.ts`:
он читает только нужные источники через обычные API с действующими правами.
Список сметы содержит позиции, количество, цену, сумму, НДС, срок и поля;
финансы рассчитываются теми же функциями, что в приложении. Статус этапа
берётся из подтверждений, а не из наличия сформированной формы документа.
Есть ответы по участникам проекта, компаниям и реквизитам, договорам,
исполнению, закрытию, входным данным и связям процесса. По явному запросу
текста документов используются существующие рендереры исполнения/закрытия.
Вложения показываются по метаданным, содержимое загруженных файлов не разбирается.

Вопрос «Кто в моей команде?» возвращает имена и должности из того же
справочника и с той же фильтрацией скрытых профилей, что раздел «Команда».
Большие списки показываются страницами с явным количеством записей.
Фактические ответы обходят очередь модели и не кешируются между запросами:
изменения сметы и прав учитываются при следующем вопросе. Имена проектов
разрешаются на сервере только среди доступных текущему пользователю.
Модель для свободных формулировок держится в памяти 10 минут, лимиты 2 CPU
и 2 ГиБ RAM не изменены.

Вопросы о формулах прибыли, НДС, выручки и рентабельности обрабатываются без
модели: помощник показывает формулу, способ задания выручки и подстановку
текущих сумм из сметы. Без выбранного проекта сначала объясняет формулы,
затем предлагает проекты для расчёта. Числовые выражения и проценты считает
ограниченный арифметический парсер без выполнения кода.

Вопросы о доменах и связях сервисов читают те же доступные карточки, что и
карта взаимосвязей. Ответ различает явные ссылки, путь через карточку сервиса
и совпадения заполненных полей. Совпадения названия/сайта не включаются в
подтверждённое размещение домена. Секретные поля, пароли, логины, заметки и
учётные данные в URL не попадают в проекцию графа или модель. Файлы и внешние
сервисы для проверки доменов не опрашиваются.
Проверка: `docker compose exec -T app node --input-type=module < tests/assistant-calculations.integration.mjs`.

Ближайшие и просроченные подписки помощник читает из доступных карточек через
те же источники, что и страница подписок. Ближайший срок выбирается среди
сегодняшних/будущих, все подписки на эту дату показываются вместе;
просроченные отмечаются отдельно. Цена и срок конкретной подписки требуют
названия или выбора карточки. Сравнение дат ведётся по Москве. Неподдержанный
фактический вопрос вызывает уточнение, а не генерацию названий, дат или сумм
из справки. Модель и её ресурсные ограничения при этом не меняются.

Уточнения «домен», «хостинг», «почта» сужают подписки по названиям, меткам
полей и явно привязанным карточкам. Если совпадений нет, общий список не
подставляется. Вопросы об уже оплаченных подписках читают историю по `paidAt`,
с границами периода в часовом поясе Москвы и отдельными итогами по валютам.
Общие платежи дедуплицируются. Автор оплаты в текущей схеме истории не хранится:
ответ показывает доступные записи хранилищ, а не приписывает их текущему человеку.

Для размещения данных Ollama на SSD есть `docker-compose.ssd.yml`.
После остановки модели скопируйте всё содержимое старого тома и проверьте
контрольные суммы. Укажите существующий путь `OLLAMA_DATA_DIR` в `.env` и
добавьте `docker-compose.ssd.yml` в `COMPOSE_FILE` после локальных override-файлов.
Например для этой машины:
`COMPOSE_FILE=docker-compose.yml:docker-compose.override.yml:docker-compose.ssd.yml`
и `OLLAMA_DATA_DIR=/Volumes/KINGSTON/MagnatPassword/ollama`.
Bind-монтирование не создаёт отсутствующий путь автоматически: KINGSTON должен
